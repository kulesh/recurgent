A paper, its patterns, and their Ruby  ·  temporal × spatial composability

Cordis in Ruby

Shi, Zhang & Cui's A Programming Paradigm for Spatiotemporal Composability asks what it takes to add and remove software components while the system runs — and answers with two runtime mechanisms: effects that carry their own inverses, and dependencies that react to context change. This page distills the paper into language-agnostic patterns and implements them as dependency-free Ruby: the revertible-effect and reactive-coeffect machinery of §3, the fiber calculus of §4 as an executable operational semantics whose metatheory is checked over randomized schedules, and the declarative loader of §5. Orientation

The idea: undo for time, contracts for space

Static composition — imports, function calls, inheritance — is resolved before a program runs and never changes. Plugin hosts and self-evolving agent harnesses need the opposite: components that arrive, depart, and get replaced during execution. The paper names the two guarantees that make that safe (§1.1):

Temporal composability — removing a component must completely revert what it did to the shared environment. The theory of effects describes how computations modify their environment; the paper lifts it to runtime by demanding every effect carry an inverse, and by making the runtime track those inverses (§3.1).

Spatial composability — components must declare what they need from one another, and the system must resolve those needs as they appear and disappear. The theory of coeffects describes what computations require of their environment; the paper lifts it to runtime by classifying every context change against every declared requirement (§3.2).

The unification is the quiet punchline: the dependency table is the context that effects act on. Providing a dependency is an effect, so it is revertible; revoking one is a revert, so it is classified — and component lifecycle stops being something you call and becomes something that happens to a component when the context around it changes. In the paper's words: "coeffect operations are effects, and effects are revertible" (§3.2.1).

From there the paper scales the guarantee from one component to a whole system: the context paradigm and its calculus. An observational equivalence on the coeffects supplies the independence that out-of-order withdrawal needs (§3.3); components become fibers with a reactive lifecycle driven by comparing a target view against a committed view, a guard that orders withdrawals behind their dependents, and failure routed through recovery (§4). The metatheory ends at confluence: whatever loads, unloads, and swaps a running system has been through, it quiesces exactly where a from-scratch assembly of the final configuration would (Theorem 73) — the licence for declarative configuration and hot module replacement (§5.2).

Distillation

Nineteen patterns, language-agnostic

The paper's machinery decomposes into patterns any runtime can adopt — an object heap, a plugin host, an agent harness. Pseudocode here is deliberately generic; the next section is the paper itself; the one after that is the Ruby. Chips under each card link both ways. The first three groups carry §3's local guarantees; the last three scale them to whole systems.

Foundation

P1Reified Context

Make the environment a first-class value, so side effects become data you can store, compose, invert, and classify.

impure  f : X → Y                 # effects hidden in the world
pure    f : (Γ, X) → (Γ, Y)       # the world is a parameter
a side effect is now just a transformation Γ → Γ

Everything else follows from this move. The paper performs it twice: once for effects (the context Γ an effect transforms) and once for coeffects (the dependency table Σ a component reads) — then reveals they are the same object.

Paper §3.1.1 Def 22 §2.3 Ruby CoeffectContext

Temporal — undo as structure

P2Witnessed Undo

Every mutation returns, along with the new state, an inverse chosen at that state — and the inverse provably reverts it.

effect(ctx):
  ctx′  = transform(ctx)
  undo  = λc. restore what ctx held    # chosen here, not a priori
  # the witness contract:  undo(ctx′) == ctx
  return (ctx′, undo)

This is the Command pattern with its debt paid: the undo is not a best-effort method but a per-state function with a checkable contract (g(δ) = γ). A fixed, state-independent undo is the degenerate case.

Paper Def 8 Def 1 Ruby Effect

P3Undo Accumulator

Pair the live state with the running composition of every inverse; unloading is applying that composition.

state   = (ctx, φ)                  # φ starts as identity
apply   : (ctx, φ) → (e.fwd(ctx), φ ∘ e.undo)
unload  : ctx ← φ(ctx); φ ← id
invariant, checkable anywhere:  φ(ctx) == ctx₀

Recovery stops being a cleanup routine someone remembered to write and becomes a structural guarantee — the soundness invariant φ(γ) = γ₀ holds at every reachable state, so "can we unload cleanly?" is a runtime assertion, not a hope.

Paper Def 2 Def 3 Def 6 Thm 7 Ruby EffectContext

P4Reversed-Order Composition

Compose do/undo pairs so that doing chains forward while undoing accumulates backward.

(f ⋄ g)(ctx):
  (c₁, undo_g) = g(ctx)
  (c₂, undo_f) = f(c₁)
  return (c₂, undo_g ∘ undo_f)      # undo f first, then g

The reversal is what makes composition safe: each inverse meets exactly the state its own application produced. Composition preserves the witness contract, so composite effects are as revertible as their parts — LIFO teardown for free.

Paper Def 9 Thm 10 Thm 11 Thm 16 Ruby Effect#compose

P5Undo Is Itself an Effect

Treat reverting as a first-class effect whose own inverse is redoing — so single effects can be plucked out of history.

apply(e) at (ctx, φ) also yields:
  undo★ = track(e.undo, e.fwd)      # redo is the undo's undo
undo★ may run later — after other effects have moved the state —
and withdraws e's contribution, nothing else

All-or-nothing rollback can't remove one plugin from the middle of a running system. Lifting undo to the effect level gives selective revert, and the soundness invariant survives it in every case.

Paper Def 12 Thm 13 Thm 15 Ruby EffectContext#apply

P6Independence Buys Any-Order Teardown

When effects commute and never disturb each other's inverses, components can be withdrawn in any order — not just last-in-first-out.

independent(e₁, e₂) ⇔
    every transformation of one commutes with every one of the other
  ∧ neither moves the inverse the other yields
keyed store + disjoint keys  ⇒  independent, for free
⇒ any permutation of the reverts reaches ctx₀

This is why the dependency table is the right shape for the shared context: effects confined to their own keys are independent by construction, and real systems unload components in arbitrary order.

Spatial — dependencies as data

P7Dependencies as Typed Data

Model the dependency registry as a typed partial map with preconditions — and make provision itself a witnessed effect.

provide(k, v) : σ → (σ[k↦v], λσ′. σ′ \ k)   # an effect, so revertible
get(k)        : defined only when k ∈ dom(σ)
never provide the same key twice; never revoke the absent

The IoC container, formalized. Because provision is an effect, registrations are tracked and recovered by the temporal machinery with no extra code — the synergy the whole paradigm rests on.

Paper Def 22 Def 23 Def 24 Ruby CoeffectContext Coeffects

P8Declared Needs, Classified Transitions

Components declare a dependency set; every context transition is classified against every declaration.

satisfied(d, σ)  =  d ⊆ dom(σ)
notify(d, σ, σ′) =  activating | deactivating | neutral
every mutation is an effect ⇒ no transition escapes classification

Reactivity here is algebraic, not infrastructural: no polling, no event bus to forget to subscribe to. Because all mutation flows through effect functions, satisfaction change is detectable at every effect boundary — the classification is total.

Paper eq. 24 Def 25 Def 26 Ruby Coeffects.notify

P9Withdraw After Deactivation

Before a key disappears, deactivate everything that declared it — teardown order is derived from the dependency graph, not hand-maintained.

withdraw(k):
  for each active c with k ∈ c.requires: deactivate(c)
  then remove k
# deactivation replays c's inverses, which withdraw c's own keys
# ⇒ the cascade recurses in exactly the right order

Notification alone can't keep a binding alive while a dependent tears down; the ordering is a constraint on other components. The excerpt states the requirement and defers the formal machinery to §4.3.1 — this is the natural operational reading.

Paper §3.2.2 §3.1.3 Ruby System#transition

P10Isolation Realms

Resolve the same logical key to different values in different contexts by adding a realm layer — sandboxing as data, not machinery.

resolve(k) = ρ(k), defaulting to k itself
isolate(k, r): derive a fresh context with ρ[k↦r]
               # shared table untouched — no inverse to track
reads and writes at k now land in realm r

Isolation is a derived realization: it returns a new context instead of mutating the shared one, so recovery is discard. Multi-tenancy, test doubles, and per-component sandboxes fall out of one two-layer lookup.

Paper Def 27 Def 28 Def 29 Ruby IsolatedContext

Unified

P11Components React, They Aren't Called

A component is a dependency specification plus tracked effects; its whole lifecycle is a function of context transitions.

component = (requires: {keys}, activate: scope → effects)
on every transition (σ → σ′):
  for each mounted c:
    case notify(c.requires, σ, σ′)
      activating   → run c.activate, inverses joining φ_c
      deactivating → run φ_c, LIFO

Nobody calls start() on anything. Mount a component and it waits; provide its last missing dependency and it activates; withdraw one and it deactivates — cleanly, because φ_c was maintained by construction. Hot module replacement is just unmount + mount.

Paper Def 26 §3.2.2 §3.1.3 Ruby Component · System

P12Undo Up To Observation

Recovery cannot restore the physical state as it stood — compare states by what observers can distinguish, not by representation.

free() does not restore the heap layout malloc() saw;
a regenerated name is not the one that was discarded
⇒ read every recovery equality up to ≃, assembled per key:
   σ ≃ σ′  ⇔  same keys, values indistinguishable by k's own operations

Each key carries its own equivalence — the coarsest relation its operations respect. States a test can't tell apart are recovered states. This is what makes "the context is recovered exactly" honest for allocators, handles, and generative names.

P13Commutative Keys Buy System-Wide Independence

Publish interfaces whose operations commute — registration tables, not ordered chains — and whole-system independence follows for free.

routes.add(a); routes.add(b)   ≃  either order   # commutative key
chain.push(a); chain.push(b)   ≠  either order   # order-sensitive key
distinct keys: independent outright
⇒ a component's effects commute with every other component's

Commutativity is the provider's obligation: it is a property of the interface a key publishes. Meet it and the assumption independence left open in §3.1.3 is discharged — Corollary 21's any-order withdrawal holds for a whole system of interleaved components.

The calculus — lifecycle as operational semantics

P14Fibers, and a Context That Is Derived

Separate the program (component) from its instantiation (fiber); never store the shared context — derive it from whoever is Active.

component = (requires d, provides p, effect e)   # a program
fiber     = ⟨d, p, e, parent, own-table σ, retired, lifecycle⟩
σ_γ = ⋃ { σ_m | m is Active }     # the context nobody owns
provider(k) is unique: provisions are disjoint

Each fiber writes only its own table; the shared context is a view, not a store. A fiber that stops being Active stops providing by definition — no unregistration code exists to forget.

Paper Def 43 Def 44 eq. 40 Ruby Fiber · Machine#sigma

P15Target View vs Committed View

Drive every lifecycle transition by comparing two resolutions: what a fiber should run against, and what it committed to.

target(n)  = ⊥ if retired or deps unsatisfied,
             else { each declared key ↦ its provider }
committed  = the resolution the last activation recorded
target ≠ committed  ⇒  a transition is due — in either direction

Record provider identity, not values: a replaced provider can never be mistaken for the one it replaced, even when both provide equal values. One comparison subsumes retirement, dependency loss, and provider replacement — and no transition ever installs effects against a resolution that shifted under it.

Paper Def 46 Thm 64 Ruby Machine#target

P16The Withdrawal Guard

Stop providing first; tear down while your bindings stay readable; remove them only when no dependent still resolves to you.

L-Leave : mark Unloading — instantly out of σ_γ, so dependents
          recompute an unsatisfied target and begin their teardown
guard   : withdrawal blocked while ∃ dependent whose committed
          view names you
L-Unload: guard clear → run accumulator, discard committed view

A dependent closing a connection pool needs the very coeffect being withdrawn. The two-phase exit delivers it: visibility through the committed view, ordering through the guard — and the guard cannot deadlock, because a Leaving provider is already invisible to fresh resolutions.

Paper Def 50 Thm 63 Thm 66 Ruby Machine#l_unload

P17Iterate, Divert, Raise — Every Exit Recovers

Run an activation as an iterator of effects; between iterations the world may move, and every early exit routes through the same recovery.

each iteration yields (state′, inverse, continuation?)
target turned mid-transition → divert: unwind what ran so far
iteration raised             → raise:  unwind, record the error
a fiber in flight must land first     # inertia — then deactivate

The iterator is a reified delimited continuation — yield, in mainstream clothes. Failure is not propagated but recorded per fiber after recovery, so a component that refuses to start leaves its siblings running and the invariant intact.

Paper Def 51 L-Raise §4.3.3 Ruby Machine#l_raise

Systems

P18Confluence Is the Reconciliation Licence

Prove (or test) that dynamic history leaves no trace — then reconcile configuration incrementally and trust the result.

whatever was loaded, swapped, unloaded along the way:
  quiescent state == from-scratch load of the final config
⇒ an orchestrator edits a declarative record of entries;
  the loader applies the least disruptive per-field operation;
  nothing else needs re-verifying

This is the dynamic-composition analogue of incremental computation's consistency with from-scratch evaluation. Without it, every reconciliation strategy needs its own proof; with it, they are all the same state.

Paper Thm 73 Def 74 §5.2.1 Ruby Reconciler

P19The System Boundary

An inverse reaches only what the system exclusively controls — draw that boundary per location, and treat emissions differently from acquisitions.

inside  : exclusively modifiable + restorable → tracked, recovered
outside : acts as identity on Γ — neither tracked nor recovered
acquisition (open, malloc, fork): a record inside — revertible
emission (write, send): crosses the boundary — withhold, or
                        compensate up to a coarser equivalence

A coeffect moves the boundary: reifying an external location confines access to operations that supply inverses. What cannot be inverted is withheld until it is safe, or compensated — the same LIFO composition, a coarser equivalence.

Paper §6.1 Def 33 Ruby Machine (boundary = own tables)
